# Database schema

Every table, column and constraint in the Linework Postgres database, and why
each one is shaped the way it is.

Generated by reading the **live database**, not the migration files. Those two
have been out of sync before: three migrations were applied to the database
without being recorded in Supabase's migration history and had to be repaired
with `supabase migration repair`. When this document and
`supabase/migrations/*.sql` disagree, re-read the live schema before trusting
either.

- **Engine:** PostgreSQL (Supabase, `us-west-2`, Pro tier)
- **Connection:** the app connects over the transaction pooler (port 6543) with
  `prepare: false`, because the pooler does not support prepared statements.
  One-shot scripts use the direct connection (5432).
- **Tables:** 9
- **Row counts at the time of writing:** 585 datasets, 102 guesses,
  142 sessions, 4 users

## Access control

Row Level Security is **enabled on every table with zero policies, and
deliberately NOT forced**, plus an explicit `REVOKE ALL FROM anon,
authenticated`.

That combination is doing three different jobs:

- Supabase exposes every table over PostgREST to the public internet via the
  anon key. RLS with no policies denies that path entirely.
- Forcing RLS would apply it to the table owner too, and the app connects as
  the owner, so forcing would lock out our own writes.
- Revoking the grant is defence in depth: even a policy added by accident later
  exposes nothing, because the privilege itself is gone.

The app never uses PostgREST or the Supabase client SDK. It talks to Postgres
directly through one pooled connection.

## The two data pipelines

The most important structural fact about this schema. There are two separate
identities and they never merge.

**The anonymous pipeline** is `sessions` and `guesses.session_id`. It contains
no raw IP addresses, no raw user agents, no coordinates, nothing identifying.
`session_id` is always present on a guess.

**The account pipeline** is `users` and `guesses.user_id`. It contains real
personal data, because an account cannot exist without something identifying.
`user_id` is **additional and nullable, never a replacement** for `session_id`.

Deleting a user sets `guesses.user_id` to null rather than deleting the guess:
the drawn path is research data independent of who drew it. The practical
consequence, learned the hard way during a data cleanup, is that **removing
fabricated accounts does not remove their guesses** — those rows stay behind as
"anonymous" and keep feeding every aggregate. Delete the guesses first.

## The four states, and why they are four columns

Collapsing any two of these has already caused a production bug, so they are
worth stating separately.

- **`verified`** — a human checked the numbers. Answers "do I trust this data".
- **`is_active`** — servable at all. Gates `POST /api/guess` and
  `GET /api/crowd/[slug]`, and is what "Your answers" filters on.
- **`in_rotation`** — whether `nextChartForUser` may serve it. A held-back chart
  is still active: still playable by direct link, still in the history of
  anyone who answered it. It is simply not offered to new players, so answers
  concentrate and charts can reach the crowd threshold.
- **`retired_at`** — withdrawn from circulation entirely.

`retired_reason` exists because the two ways a chart gets retired have
different durability. `'catalogue'` means the slug left `scripts/wb-catalogue.ts`
and is cleared automatically when it returns. `'admin'` means a human took it
out, and the seed must never clear it — otherwise an admin's decision would
silently expire on the next import.

`is_active = false` is ambiguous on its own: it means both "not yet reviewed"
and "deliberately withdrawn". That ambiguity caused a real incident. A bulk
activation read 289 just-retired charts as "green, imported, inactive" and
turned them all back on, putting 564 charts live instead of 275. `retired_at`
plus a CHECK constraint is the durable fix.

## `reliability` is a separate axis from `verified`

`verified` means a human checked it. `reliability` describes where the numbers
came from:

- **green** — the source's own published values, fetched from a named indicator
  and never interpolated. Green asserts *here is how to check me*, not *I am
  confident*: a green row must carry a `source_series_id` so re-running the
  importer reproduces the same numbers. A test fails the build if that is ever
  violated.
- **yellow** — real and sourced but carrying a named caveat.
- **red** — approximated or unconfirmed. Not publishable.

The default is `red`, never green. Unassessed and unpublishable are the same
thing, and a green default would silently bless every future insert.

Collapsing the two would let a script mark its own output human-approved.

## Constraints

| Constraint | Enforces |
|---|---|
| `datasets_active_requires_verified` | `NOT is_active OR verified` |
| `datasets_retired_not_active` | A retired chart cannot be served |
| `datasets_retired_pair` | `retired_at` and `retired_reason` are both set or both null |
| `datasets_retired_reason_valid` | Only `'catalogue'` or `'admin'` |
| `datasets_verified_needs_a_date` | `verified` iff `verified_on is not null` |
| `datasets_reliability_has_note` | Non-green requires a note of 1 to 600 chars |
| `datasets_series_are_arrays` | Both series are jsonb arrays |
| `datasets_series_lengths_match` | `x_values` and `y_values` are the same length |
| `datasets_reveal_index_leaves_room` | Between 1 and `length - 2`, so there is always something to draw |
| `datasets_domain_ascends` | `y_domain_max > y_domain_min` |
| `datasets_slug_is_url_safe` | `^[a-z0-9-]+$` |

The first one is the backstop for this project's central promise: unverified
data must never reach production. Build-time validation checks it too, but
application code can be bypassed or buggy and a constraint cannot.

# `guesses`

One drawn line. **This table is the research output.** 102 rows.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | bigint | no | Primary key. Global, not per-dataset |
| `session_id` | uuid | no | The anonymous identity. Always present |
| `user_id` | uuid | yes | Additional, never a replacement. `on delete set null` |
| `dataset_id` | bigint | no | `on delete restrict` |
| `created_at` | timestamptz | no | |
| `path` | int2[] | no | **The drawn line.** 40 points, y quantized to 0..1000 |
| `path_resolution` | smallint | no | Always 40 in practice |
| `order_in_session` | smallint | no | 1-based position within the sitting. **Not dense** (see below) |
| `draw_ms` | int | no | Duration of the final accepted stroke only |
| `redraw_count` | smallint | no | Hesitation signal |
| `viewport_w` | int | no | |
| `score` | smallint | no | `round(100 * exp(-4 * mean_abs_error))` |
| `mean_abs_error` | float8 | no | Mean \|guess − truth\|, normalised 0..1 |
| `mean_signed_error` | float8 | no | Mean (guess − truth). **The most important column** |
| `is_suspect` | bool | no | Excluded from every published aggregate |
| `suspect_reasons` | text[] | no | Why. Must agree with `is_suspect` |

## `path` is the dataset

40 points, y quantized to integers 0..1000 normalised across the chart's
`[y_domain_min, y_domain_max]`. The three summary columns are averages over
those 40 points and cannot distinguish someone uniformly a little wrong from
someone who traced the first half perfectly and then went badly off. Those are
different beliefs. Any real analysis reads `path`.

## `mean_signed_error` is the point

Absolute error says people are wrong. Signed error says **which direction**,
and a direction that holds across many people is a claim about public belief.

Positive means the player drew **above** the truth. Note that "overestimated
the value" is not the same as "overestimated the problem" — on a child
mortality chart, drawing high means believing the world is worse than it is; on
a vaccination chart it means believing it is better. The direction of the value
is what is stored; the direction of the belief has to be read per chart by a
human.

## `order_in_session` is not dense

It is assigned at write time and never renumbered, so deleted rows leave
permanent holes. Production currently contains a session with 28 rows spanning
positions 1 to 33.

This matters for analysis. A funnel that counts sessions per stored position
can go **up** where a hole falls, which is exactly what happened the first time
`analysis/04_funnel.sql` was run — it reported 150% continuation at step 11.
Recompute the step with `row_number()` over surviving rows instead.

## Suspect flagging

Set at write time in `lib/server/suspect.ts`:

| Reason | Fires when |
|---|---|
| `zero-variance` | Every point in the path is identical |
| `too-fast` | `draw_ms < 300` |
| `duplicate-in-session` | This session already answered this chart |
| `headless-agent` | The user agent matched a known automation signature |

Reasons **accumulate** rather than short-circuit: a row guilty of three records
three, so the flag can be audited rather than merely trusted.

The duplicate check is not decidable in the pure function — it needs a database
read — so `recordGuess()` does the authoritative check *inside the same
transaction as the insert*, under `select ... for update` on the session row.
Two guesses posted at once for one session cannot both land as "first" with
neither flagged.

## Constraints

| Constraint | Enforces |
|---|---|
| `guesses_path_matches_declared_resolution` | `array_length(path, 1) = path_resolution` |
| `guesses_path_values_in_range` | Every element in 0..1000, via `path_values_in_range()` |
| `guesses_path_resolution_is_sane` | 2 to 1000 |
| `guesses_errors_are_unit_scaled` | `mean_abs_error` in 0..1, `mean_signed_error` in −1..1 |
| `guesses_score_is_a_percentage` | 0..100 |
| `guesses_suspect_matches_reasons` | `is_suspect` iff `suspect_reasons` is non-empty |
| `guesses_counters_are_not_negative` | `draw_ms`, `redraw_count` ≥ 0; `order_in_session` ≥ 1 |
| `guesses_viewport_is_plausible` | 1 to 20000 |

`path_values_in_range()` is a small immutable SQL function because a CHECK
constraint cannot contain a subquery, and there is no other way to range-check
an array element-wise.

# `sessions`

One per visit. Anonymous by construction. 142 rows.

| Column | Type | Null | Notes |
|---|---|---|---|
| `id` | uuid | no | Minted in `middleware.ts`, stored in the `dtl_session` cookie |
| `created_at` | timestamptz | no | |
| `country` | text | yes | ISO-2 from `x-vercel-ip-country`. Never a coordinate |
| `device_type` | text | yes | `mobile` / `tablet` / `desktop` / `unknown` |
| `referrer_host` | text | yes | **Hostname only**, no path, no query string |
| `ua_hash` | text | yes | Salted SHA-256. Storing the raw user agent is forbidden |
| `is_suspect` | bool | no | |

## Why each field is shaped this way

`ua_hash` is SHA-256 with a server-only pepper (`SESSION_HASH_SECRET`) that
never touches the database. Without the pepper, hashing a user agent buys
nothing: the space of real UA strings is small enough to enumerate, so an
unsalted hash is obfuscation, not anonymisation. A missing or short pepper is a
hard throw, not a warning, because a silent fallback is exactly how a no-PII
promise quietly stops being true. Rotating the pepper severs the link between
old and new hashes, which caps how long any pseudonymous identifier stays
useful.

`referrer_host` is stripped to a hostname because query strings carry things
people did not mean to send.

`device_type` is four coarse buckets, deliberately too blunt to help identify
anyone.

The row is created **lazily, on the first guess**, not on page view. A write per
page view would put Postgres in the critical path of first paint and create a
row for every crawler that never draws anything. But the inbound referrer is
only visible on the very first request, so middleware captures it once into a
short-lived `dtl_ref` cookie for the API route to read later.

Sessions outnumber guesses because a session row is created on the first guess
of a visit and not reused across visits.

| `current_streak` / `longest_streak` | smallint | no | |
| `last_active_date` | date | yes | The day the goal was last met |
| `streak_freezes_available` | smallint | no | Capped at 3 |
| `blocked_at` / `blocked_reason` | | yes | Moderation |
| `flagged_at` / `flagged_reason` | | yes | Review, not enforcement |
| `low_effort_strikes` | smallint | no | Never auto-blocks |
| `terms_accepted_at` | timestamptz | yes | Never back-filled |
| `email_verified_at` | timestamptz | yes | Set only by completing a password reset |
| `created_at` / `updated_at` | timestamptz | no | |

## `role` is the whole admin mechanism

Admin status lives in this column and nowhere else. There is no hardcoded email
comparison anywhere in application code. `session.user.role` is read from the
database at sign-in.

A consequence of the JWT session strategy: a promoted account keeps its old
role until it signs out and back in, because nothing re-reads the column per
request.

`scripts/seed-admin.ts` pre-creates one passwordless stub. `createUser()`'s
`INSERT ... ON CONFLICT (email) DO UPDATE ... WHERE users.password_hash IS NULL`
is the claim mechanism: a conflict against a real account fails the `WHERE` so
nothing updates and it reads as "email taken"; a conflict against the stub
passes and completes it. `role` is never touched by that statement, so a
pre-seeded admin stays admin and a fresh signup gets the column default.

## Blocking is enforced per guess, not at sign-in

The session strategy is JWT, so a token minted before a block stays
cryptographically valid and NextAuth keeps accepting it without consulting
Postgres. A sign-in-only check would let a blocked player keep submitting until
their token expired. `isUserBlocked()` runs on every guess and **fails closed**,
deliberately unlike the rate limiter which fails open: a moderation decision
must not be undone by a database blip, but a limiter should not take signup
down with it.

## `email_verified_at` has one honest job

Email confirmation was removed once password reset no longer depended on it —
it gated nothing. The column was kept and repurposed: it is now set only by
completing a password reset, which genuinely proves the mailbox works. If
someone reports that a reset email never arrived, this is the only evidence the
database holds about whether that address receives mail at all.

## Streak columns are derived state, and have been wrong twice

They are maintained incrementally by application code. Both failures left the
underlying guesses intact:

1. `maybeAdvanceStreak()` was called without `await`, on the reasoning that a
   streak failure must never fail a guess that already landed. The reasoning
   was right and the mechanism was wrong: a serverless instance can be frozen
   the moment it responds, so an un-awaited promise is not background work, it
   is work that usually never happens.
2. `String(date).slice(0, 10)` on a DATE column yields `"Thu Aug 27"`, never
   `"2026-08-27"`. The "already counted today" guard could never match, so the
   streak reset on every single guess. Fixed with a shared `toDateOnly()`
   helper.

Fixing the first exposed the second. Both times the repair was to rebuild
streaks from `guesses`, the only record that was never lossy.
`analysis/11_engagement_and_streaks.sql` section 4 does that recomputation so
the stored value can be checked rather than trusted.

## Constraints

`users_email_is_lowercase`, `users_email_looks_like_an_email`,
`users_display_name_is_reasonable` (1–40 chars),
`users_birth_year_is_plausible` (1900 to current year − 5),
`users_city_and_state_travel_together` (both set or both null),
`users_role_is_known`, `users_longest_streak_at_least_current`,
`users_block_has_reason` and `users_flag_has_reason` (a timestamp and a reason
are set together, 1–500 chars), `users_streak_fields_not_negative`,
`users_strikes_not_negative`.

The paired timestamp/reason constraints exist for the same purpose as
`guesses_suspect_matches_reasons`: a moderation action with no stated reason is
unauditable, and "this account was blocked" with no explanation is not a
decision anyone could defend or revisit.

# `crowd_stats`

Precomputed percentiles. One row per dataset per x position. 3,560 rows.

| Column | Type | Notes |
|---|---|---|
| `dataset_id` | bigint | Part of the composite primary key |
| `x_index` | smallint | 0..39, the same positions the path and truth share |
| `n` | int | Clean guesses for this dataset, **denormalised onto all 40 rows** |
| `p10` `p25` `p50` `p75` `p90` | smallint | On the same 0..1000 scale as `guesses.path` |
| `computed_at` | timestamptz | |

`n` is repeated on every row so a read never needs a second query to apply the
cold-start threshold.

Percentiles are stored on the same quantized scale as `path`, so nothing needs
renormalising to compare a percentile against a guess.

`crowd_stats_percentiles_ordered` enforces `p10 <= p25 <= p50 <= p75 <= p90`.
If the aggregation query is ever broken the write fails loudly instead of
shipping a band that reads backwards on screen.

# `crowd_sample`

Up to 500 raw unflagged paths per dataset, refreshed at the same cadence.
102 rows.

Not redundant with percentiles. The ink-density effect comes from many
individual translucent paths overlapping, and five summary lines cannot produce
it. Percentiles answer *where*; the sample answers *what does that actually
look like*.

## Both are rebuilt by `recompute_crowd_stats()`

Run by `pg_cron` every 15 minutes. Nothing computes them on request: the
function takes no arguments, so there is no code path that lets a request
trigger it early.

**The cold start rule.** Crowd percentile bands are never rendered below
`CROWD_MIN_N = 50` unflagged guesses. Enforced server-side in
`crowdForDataset()`: below threshold the API response is shaped as
`{ belowThreshold: true, n, minRequired }` with no percentiles and no sample
field present at all, so there is no client bug that could render bands it
should not have.

A stale `computed_at` means the cron job has stopped, and it fails silently —
the crowd view just keeps showing older numbers.
`analysis/09_crowd_readiness.sql` section 4 checks for it deliberately.

# `rate_limit`

Fixed-window counters. 4 rows, disposable.

| Column | Type | Notes |
|---|---|---|
| `bucket` | text | Primary key. A salted hash, never a raw identifier |
| `hits` | int | |
| `expires_at` | timestamptz | |

Serverless functions share no memory, so a rate-limit counter needs somewhere
both instances can see. The increment is a single
`INSERT ... ON CONFLICT DO UPDATE ... RETURNING`, so it is atomic under
concurrent hits from one bucket. Expired rows are swept opportunistically on
about 2% of requests rather than needing a cron for one small table.

**A client is not a person.** This assumption has been wrong three separate
times in this codebase — the email limiter, the per-client email cap, and the
signup limit. An office, a campus, a household and a mobile carrier's CGNAT are
all one public address shared by many people. Limits sized as though one IP is
one human lock real users out. Current limits: 30 guesses/minute,
120 signups/hour, 10 sign-ins/minute, 5 emails/hour per address and 20 per
client.

# `email_tokens`

Password reset tokens. Hash only.

| Column | Type | Notes |
|---|---|---|
| `user_id` | uuid | `on delete cascade` |
| `purpose` | text | `'verify_email'` or `'reset_password'` |
| `token_hash` | text | Unique. **Only the hash is stored** |
| `expires_at` / `consumed_at` / `created_at` | timestamptz | |

A database dump yields no working links. Unlike a password this is a plain
SHA-256, deliberately: the input is 32 bytes from `randomBytes`, so there is no
dictionary to precompute and nothing for a salt to defeat — and the token is
*found* by its hash, which a per-row salt would make impossible without
scanning every row.

Changing a password kills every outstanding token in the same transaction.
Otherwise a reset link sitting in an inbox stays usable after the owner
recovers the account, so an attacker who triggered a reset earlier could take
it straight back.

# `email_log`

Diagnostic, not an archive. 6 rows.

| Column | Type | Notes |
|---|---|---|
| `to_email` | text | **Masked** (`r***@gmail.com`) |
| `kind` | text | |
| `ok` | bool | |
| `error` | text | The provider's verbatim message |
| `created_at` | timestamptz | |

Exists because email failure was invisible. `/password/forgot` must answer
identically in every case or it becomes an account-enumeration oracle, so
"nothing arrived" and "everything worked" looked the same to the only person
who could act on the difference. The provider's explanation was going to a
server log nobody reads.

No body, no link, no token: storing a body would put live reset links in a
table, which is exactly what storing only token hashes was meant to prevent.
The recipient is masked so the log answers "did sending break and what did the
provider say" without being a record of who used the site and when.

# Functions

| Function | Purpose |
|---|---|
| `path_values_in_range(int2[])` | Immutable helper for the `guesses` CHECK constraint |
| `recompute_crowd_stats()` | Rebuilds `crowd_stats` and `crowd_sample`. Takes no arguments by design |
| `touch_updated_at()` | Trigger function maintaining `updated_at` |

## The scaling ceiling in `recompute_crowd_stats()`

The sampling query uses `ORDER BY random()` inside a `row_number()` window to
get an even sample per dataset, which requires a full sort of every unflagged
row for that dataset on every run. That is the piece that degrades first.

Measured today at n≈102: 0.234 ms of actual database execution.

Expect to start paying attention around **50,000 to 100,000 unflagged guesses
in a single dataset**, where an in-memory sort of that many rows approaches
`work_mem` and risks spilling to disk. Past roughly **500,000 to 1,000,000** it
needs real work regardless, because resorting the entire table from scratch
every 15 minutes is fundamentally wasteful once most of it has not changed.

The fixes, in the order to reach for them:

1. Reservoir sampling maintained at write time (Algorithm R in a trigger):
   O(1) per guess instead of O(N log N) per cycle.
2. Incremental percentiles from a bucketed histogram updated per insert.
   A t-digest would be more accurate but needs an extension not confirmed
   available here; a histogram needs nothing new.
3. Partition `guesses` by `dataset_id`, so one large dataset's cost stops being
   coupled to how many other datasets exist.

# Two things that are not enforced by the database

Worth knowing, because they look like they ought to be.

**Red charts must never be in circulation.** This is policy, not a constraint.
`analysis/13_integrity_checks.sql` section 8 asserts it.

**The scoring maths exists twice.** `truthPathNormalized()` and `scoreGuess()`
live in `lib/scoring/score.ts`, and `analysis/07_shape_of_error.sql` reproduces
the resampling in SQL. Nothing automatically checks the two agree.
`analysis/13_integrity_checks.sql` section 1 is that check: it recomputes
`mean_abs_error`, `mean_signed_error` and `score` from the raw path and
compares against what the server stored. It currently passes on all 102 rows
within 1e-9.
